# GymLog Strava Integration Brief

Status: Edge Functions implemented; deployment and frontend controls pending
Last Updated: 2026-09-24

## Current Implementation

GymLog is a React 19 + TypeScript application built with Vite 8.

- Runtime: browser-based PWA
- Base path: `/fitapp/`
- Hosting assumption: static frontend deployment
- Package manager/runtime: Node.js with npm
- Authentication: Supabase Auth with Google OAuth
- Database: Supabase PostgreSQL
- Authorization: PostgreSQL Row Level Security
- Client SDK: `@supabase/supabase-js` 2.117.1
- Charts: Recharts
- Export/import: JSON backup plus SheetJS/xlsx support
- Location: browser Geolocation API
- Offline behavior: not supported for normal data operations; the PWA shell may be cached, but data access requires the network

The shared Supabase client is in `src/lib/supabase.ts` and uses the generated contract in `src/lib/database.types.ts`.

The current frontend only exposes the Supabase publishable key. No server-side Supabase Edge Function, backend service, Strava client secret, webhook endpoint, or scheduled job exists yet.

## Current Authentication Model

GymLog currently allows one owner account:

- Provider: Google
- Allowed email: `miroslav.vicher@gmail.com`
- Supabase RLS policies restrict data to that identity
- Other authenticated Google accounts are rejected by the frontend and blocked by database policies

## Recommended Strava Architecture

Use Supabase Edge Functions as the Strava OAuth and API boundary.

```text
GymLog browser
    |
    | Supabase session
    v
Supabase Edge Function
    |
    | Strava client ID + client secret
    v
Strava OAuth/API
```

The browser should never receive or store the Strava client secret. Prefer keeping Strava refresh/access tokens in a protected server-side table accessed only by Edge Functions. The browser calls an Edge Function using the existing Supabase session.

Recommended functions:

- `strava-start-oauth`: validates the GymLog user and returns or redirects to the Strava authorization URL
- `strava-oauth-callback`: exchanges the authorization code and stores the token securely
- `strava-status`: returns connection state and basic athlete information, never raw tokens
- `strava-disconnect`: revokes/deletes the stored connection
- `strava-upload-workout`: refreshes the token if necessary and uploads a completed GymLog workout
- optional `strava-webhook`: receives Strava activity events

For a static Vite PWA, the OAuth callback should be an Edge Function URL. After the callback completes, redirect back to the frontend route under `/fitapp/`.

## OAuth Requirements

Create a Strava API application and configure:

- Client ID
- Client secret
- Authorization callback domain/URL

The callback URL must point to the deployed Edge Function, not directly to the browser. The Edge Function exchanges the authorization code with Strava.

Request the smallest practical scope:

- `read` for athlete/basic activity reads
- `activity:write` for uploading GymLog workouts to Strava

Do not request write scope for an import-only integration.

## Proposed New Tables

### `strava_connections`

One row per GymLog user, protected by RLS and preferably writable only through Edge Functions.

Suggested fields:

- `id bigint generated by default as identity primary key`
- `user_id uuid not null references auth.users(id) on delete cascade`
- `strava_athlete_id bigint not null`
- `strava_athlete_name text`
- `scope text not null`
- `access_token text not null`
- `refresh_token text not null`
- `expires_at timestamptz not null`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`
- unique `(user_id)`
- unique `(strava_athlete_id)`

Token columns should not be selected by browser-facing queries. A stronger design is to place tokens in a private schema or expose only Edge Functions that use service-role access.

### `strava_activities`

Stores imported activity metadata and provides idempotency.

Suggested fields:

- `id bigint generated by default as identity primary key`
- `user_id uuid not null references auth.users(id) on delete cascade`
- `strava_activity_id bigint not null`
- `name text not null`
- `sport_type text`
- `start_date timestamptz not null`
- `elapsed_time_seconds integer`
- `moving_time_seconds integer`
- `distance_meters numeric`
- `elevation_gain_meters numeric`
- `raw_payload jsonb`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`
- unique `(user_id, strava_activity_id)`

Add indexes on `(user_id, start_date desc)` and `(user_id, sport_type)`.

### Optional `workout_strava_links`

Use this only if a GymLog strength workout should be explicitly linked to a Strava activity:

- `id bigint generated by default as identity primary key`
- `user_id uuid not null references auth.users(id) on delete cascade`
- `workout_id bigint not null`
- `strava_activity_id bigint not null`
- `created_at timestamptz not null default now()`
- unique `(workout_id)`
- unique `(user_id, strava_activity_id)`

## Data Model Decision Needed

Strava activities are usually endurance/cardio activities, while GymLog records detailed strength sets. Decide which behavior is wanted before coding:

1. **Upload GymLog workouts**
   - Generate a TCX WeightTraining activity from GymLog sets.
   - Upload it when an unfinished workout is closed on a later day.
   - Keep a link so the same workout is not uploaded twice.

2. **Link activities to GymLog workouts**
   - Let the user manually connect a Strava activity to a workout.
   - Preserve both systems' records.

3. **Create GymLog workouts from Strava activities**
   - Requires mapping sport types to GymLog semantics.
   - Does not naturally provide exercise/set/weight/repetition data.
   - Should not silently create strength workouts from incomplete activity data.

4. **Import Strava activities**
   - Not part of the current integration direction.

The lowest-risk first release is option 1, followed by optional manual linking.

## Supabase Environment and Secrets

Browser-visible variables:

```env
VITE_SUPABASE_URL=...
VITE_SUPABASE_PUBLISHABLE_KEY=...
```

Server-side Edge Function secrets only:

```env
STRAVA_CLIENT_ID=...
STRAVA_CLIENT_SECRET=...
STRAVA_REDIRECT_URI=...
```

Never place `STRAVA_CLIENT_SECRET`, Supabase service-role keys, or Strava refresh tokens in `VITE_*` variables, committed files, or browser storage.

## Sync and Reliability Rules

- Use `(user_id, strava_activity_id)` as the idempotency key.
- Refresh expired access tokens with the refresh token in the Edge Function.
- Store the new refresh token when Strava rotates it.
- Handle revoked access by marking the connection disconnected and asking the user to reconnect.
- Respect Strava rate limits and avoid repeated full-history imports.
- Store a `last_synced_at` value or sync cursor per user.
- Paginate Strava activity requests.
- Make sync retryable and safe to repeat.
- Treat Strava as an external source; do not delete local imported activities merely because one sync response omitted them.

## Implemented Edge Functions

- `strava-start-oauth`: validates the Supabase owner session and returns a signed-state Strava authorization URL.
- `strava-oauth-callback`: validates state, exchanges the authorization code, and stores tokens server-side.
- `strava-status`: returns connection metadata without tokens.
- `strava-disconnect`: revokes the Strava token when possible and removes the local connection.
- `strava-upload-workout`: refreshes expired tokens, generates a TCX WeightTraining activity, and uploads it idempotently.

Required Edge Function secrets are listed in `supabase/functions/.env.example`. Set `STRAVA_FRONTEND_REDIRECT_URI` to the deployed `/fitapp/settings?strava=callback` URL before deployment; the example uses localhost.

Deploy with the Supabase CLI after linking this project:

```powershell
supabase functions deploy strava-start-oauth
supabase functions deploy strava-oauth-callback
supabase functions deploy strava-status
supabase functions deploy strava-disconnect
supabase functions deploy strava-upload-workout
```

`supabase/config.toml` disables gateway JWT verification for all five functions. The four browser-facing functions still enforce the Google owner session in their own code; the OAuth callback validates its signed state and resolves the owner through the Supabase Admin API. All five functions are self-contained for dashboard single-file deployment.
